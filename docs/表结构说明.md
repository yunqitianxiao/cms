# 数据库设计说明

数据库 `cms_db`，字符集 `utf8mb4`，引擎 InnoDB。共 8 张表：6 张主表 + 2 张关联表。

建表脚本：`src/main/resources/sql/schema.sql`；初始化数据：`src/main/resources/sql/data.sql`。

---

## 一、实体关系

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_permission >── sys_permission
    │                              │
    │ 1:0..n                       │ 1:0..n
    ▼                              ▼
cms_article ────── n:1 ────── cms_category (自关联 parent_id，最多 3 级)
    │
    └── author_id / auditor_id 指向 sys_user

sys_log 独立记录，user_id 只做弱引用（不建外键）
```

文字表述：

- **用户与角色**是多对多。一个用户可以有多个角色，最终权限 = 所有角色权限的并集。
- **角色与权限**是多对多。权限点由初始化脚本写入，运行期只读。
- **文章与分类**是 n:1，分类必填；**文章与用户**有两个方向的引用：作者（必填）和最后审核人（可空）。
- **分类自关联**：`parent_id = 0` 表示根节点，`level` 由服务端根据父节点推导，最大 3 级。
- **操作日志**不建外键：用户被物理删除后日志仍要能追溯，所以冗余存了 `username`。

## 二、表逐张说明

### 1. `sys_user` 用户

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 主键 |
| `username` | VARCHAR(50) | 登录名，唯一，**创建后不可修改**（审计链的锚点） |
| `password` | VARCHAR(100) | BCrypt 密文，不存明文 |
| `nickname` | VARCHAR(50) | 昵称，列表展示用 |
| `email` / `phone` | VARCHAR | 联系方式，可空 |
| `status` | TINYINT | 1 启用 / 0 停用 |
| `deleted` | TINYINT | 逻辑删除标记 |
| `create_time` / `update_time` | DATETIME | 自动填充 |
| `create_by` / `update_by` | BIGINT | 操作人 |

索引：`uk_user_username(username)` 唯一；`idx_user_status(status)` 用于按状态筛选。

**为什么用户名不允许改**：日志表靠 `username` 做可读追溯，改名会让历史日志指向一个"从不存在的人"。

### 2. `sys_role` 角色

| 字段 | 类型 | 说明 |
|---|---|---|
| `role_code` | VARCHAR(50) | 角色编码，唯一；代码里的 `RoleCode` 常量与之对应 |
| `role_name` | VARCHAR(50) | 展示名 |
| `sort` | INT | 展示顺序 |
| `status` | TINYINT | 1 启用 / 0 停用 |

索引：`uk_role_code(role_code)`。

**为什么编码和名称分开**：业务判断永远用编码（`RoleCode.ADMIN`），改名不影响判断；界面上展示名称。

### 3. `sys_permission` 权限点

| 字段 | 类型 | 说明 |
|---|---|---|
| `perm_code` | VARCHAR(64) | 权限码，如 `article:audit`；唯一 |
| `perm_name` | VARCHAR(64) | 展示名 |
| `perm_group` | VARCHAR(32) | 分组，前端按组展示 |
| `description` | VARCHAR(200) | 说明 |
| `sort` | INT | 组内排序 |

索引：`uk_perm_code(perm_code)`。

**这张表只读**：启动期站点地图校验需要"权限码集合是稳定的"这一前提——如果运行期能随便加权限码，`@RequirePermission` 里写错的码就不会在启动时暴露，而是等到某次请求才 403。

### 4. `cms_category` 分类

| 字段 | 类型 | 说明 |
|---|---|---|
| `parent_id` | BIGINT | 上级分类，0 表示根 |
| `name` | VARCHAR(50) | 分类名 |
| `level` | TINYINT | 层级 1–3，**由服务端推导**，不信任客户端 |
| `sort` | INT | 同级排序 |
| `status` | TINYINT | 1 启用 / 0 停用 |

索引：`uk_category_parent_name(parent_id, name)` 保证同一父节点下不重名；`idx_category_parent(parent_id, sort)` 用于按父节点取子节点并按序排列。

**为什么 level 冗余存储**：层级上限校验发生在写入时，查询时只需要读字段；如果每次递归算层级，列表页会退化成 N 次查询。冗余的代价是父节点变化时要级联更新，而本项目不支持换父节点，逻辑上闭合。

### 5. `cms_article` 文章

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | VARCHAR(200) | 标题 |
| `summary` | VARCHAR(500) | 摘要 |
| `content` | MEDIUMTEXT | 正文（纯文本，保留换行） |
| `category_id` | BIGINT | 外键 → `cms_category.id` |
| `author_id` | BIGINT | 外键 → `sys_user.id` |
| `status` | VARCHAR(16) | `DRAFT` / `PENDING` / `PUBLISHED` / `REJECTED` / `OFFLINE` |
| `auditor_id` | BIGINT | 最后审核人 |
| `audit_opinion` | VARCHAR(500) | 审核意见 |
| `audit_time` / `submit_time` / `publish_time` | DATETIME | 三个关键时间点 |
| `offline_reason` | VARCHAR(500) | 下架原因 |
| `view_count` | INT | 阅读量 |
| `version` | INT | 乐观锁版本号 |
| `deleted` | TINYINT | 逻辑删除 |

索引与用途：

| 索引 | 覆盖的查询 |
|---|---|
| `idx_article_query(status, category_id, create_time)` | 列表页最常见的"按状态 + 分类 + 时间排序" |
| `idx_article_author(author_id, status)` | 「我的稿件」和按作者统计 |
| `idx_article_title(title)` | 标题模糊查询时前缀部分可用 |
| `idx_article_publish(publish_time)` | 前台按发布时间倒序 |

**为什么 `status` 用字符串而不是字典表**：状态是代码里的枚举，取值集合由状态机固定，任何新增状态都必须同时改代码；用字典表只会多一次 join，却制造出"库里有、代码不认识"的状态。

### 6. `sys_log` 操作日志

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | BIGINT | 操作人，未登录可空（弱引用，不建外键） |
| `username` | VARCHAR(50) | 操作人用户名冗余 |
| `log_type` | VARCHAR(20) | LOGIN / ARTICLE / AUDIT / CATEGORY / USER / ROLE / AI_QUERY |
| `operation` | VARCHAR(100) | 可读操作名，如"审核通过" |
| `method` | VARCHAR(200) | `类名#方法名` |
| `uri` / `http_method` | VARCHAR | 请求路径与方法 |
| `params` | VARCHAR(2000) | 脱敏后的入参 |
| `ip` | VARCHAR(64) | 来源 IP |
| `result` | VARCHAR(20) | SUCCESS / DENIED / FAIL |
| `error_msg` | VARCHAR(400) | 失败原因 |
| `cost_ms` | BIGINT | 耗时 |

索引：`idx_log_time(create_time)`（默认按时间倒序）、`idx_log_user(user_id)`、`idx_log_type(log_type, create_time)`。

**`result = DENIED` 是这张表最有价值的部分**：它记录的是"有人尝试了但被权限拦住"，与业务失败（FAIL）分开。没有这个区分，越权尝试会混在几百条正常报错里看不出来。

### 7. `sys_user_role` 用户角色关联

联合主键 `(user_id, role_id)`，两个外键。`idx_ur_role(role_id)` 用于"这个角色下有哪些人"和删除角色前的引用检查。

### 8. `sys_role_permission` 角色权限关联

联合主键 `(role_id, perm_id)`，两个外键。`idx_rp_perm(perm_id)` 用于按权限反查角色。

## 三、几条跨表约定

1. **逻辑删除统一用 `deleted TINYINT`**，由 MyBatis-Plus `@TableLogic` 自动拼接 `deleted = 0`。关联表（`sys_user_role`、`sys_role_permission`）不做逻辑删除，解绑即物理删除。
2. **`create_time` / `update_time` 有数据库默认值**，同时由 `MetaObjectHandler` 在 Java 侧填充。两边都写是为了：正常写入走 Java（时间统一由应用决定），绕过应用的手工 SQL 也有兜底。
3. **外键真实存在**，不靠应用层自觉。文章分类被引用时删分类会直接失败，服务层再把它翻译成 40903「数据被引用，无法删除」。
4. **排序字段不来自客户端**：接口只收 `sort=createTime,desc` 这类语义值，服务端用白名单映射成物理列名，避免 ORDER BY 注入。
