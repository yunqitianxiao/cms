## 0 一页速览

**要做成什么**

一个用 Spring Boot + Spring MVC + MyBatis-Plus 写的 CMS，四个角色（游客 / 作者 / 审核员 / 管理员）能走完「投稿 → 审核 → 上架 / 下架」全链路；接口级权限由 Spring AOP 拦截；所有写操作留日志。

在这之上加一个**站内引导智能体**：右下角悬浮球，点开是对话框。用户用自然语言问「我怎么发布文章」，智能体把相关**界面做成卡片铺在对话框里**——每张卡是一个页面，带一句话说明、关键操作、以及"要去哪、点哪个按钮"。它知道全站结构的方式是**启动时反射扫描后端 Controller 生成站点地图**，不是人工维护一份文档。

**交付边界（一句话）**

> 智能体只做「告诉你去哪、怎么点」，**不替你执行任何写操作**。它拿不到数据权限，也就无法成为越权的跳板。

**时间**

基准 18 个工作日（D1–D18）。若截止时间更紧，按 §10 的砍项顺序压缩到 12 天可交付版本。

**评分映射**：§9 逐条对齐评分表 19 行，每行给可执行的验收判据。

## 1 项目定位与范围

### 1.1 相对 D1 需求分析的变更

D1 把「极简管理页」列为**可选、不计分**。本次新增需求改变了这一点：

| 变更 | 原因 | 回填动作 |
|---|---|---|
| 前端页面从"可选"升为"必做" | 智能体的载体是对话框 UI，没有前端就没有交付物 | 需求分析 §2.1、§2.2 同步修改，Q-02 关闭 |
| 新增「站内引导智能体」模块 | 用户新需求 | 需求分析新增 §4.8 场景八 |
| 认证方案由「暂定 JWT」改为 **Session** | 前端与后端同源（Thymeleaf 直出），退出只需 `session.invalidate()`，不必维护 token 黑名单；智能体取当前用户也更直接 | 需求分析 §8 Q-01 关闭 |

> 注意：**不要在建完表之后再改认证方案**。Session 决定拦截器形态、决定前端如何带 Cookie、决定智能体如何拿当前用户，属于必须 D2 之前定死的事。

### 1.2 做什么

- 六张主表 + 两张关联表（严格对齐评分表「六表关联设计」）；
- 用户注册 / 登录 / 退出 / 角色分配 / 细粒度权限拦截（AOP）；
- 多级分类（3 级）增删改、排序、状态启停、与文章绑定；
- 文章新增 / 编辑 / 批量发布 / 下架 / 删除 / 分页 / 多条件模糊检索 / 审核状态机；
- 操作日志、统一异常、参数校验、数据安全防护；
- 进阶：高级分页查询、MP 高级特性、N+1 优化、RESTful + ApiFox 联调；
- 管理端页面（登录、文章、分类、审核、用户、角色、日志）+ 前台 2 页（文章列表、详情）；
- 站内引导智能体（本任务书 §7）。

### 1.3 明确不做（写进「不包含」，避免范围蔓延）

| 不做的事 | 原因 |
|---|---|
| Vue / React 独立前端工程 | 考核点是后端框架能力；`npm build` 在答辩环境是额外风险。前端用 Thymeleaf + 原生 JS，零构建 |
| 智能体代执行写操作（"帮我把这篇文章删了"） | 用户原话是「引导和建议」。代执行需要二次确认 + 事务边界，且把越权面放大一个量级 |
| 智能体对接业务数据的自然语言问答（"上个月发了多少篇"） | 那是 BI 查询，不是引导。混在一起会让"智能体"变成半成品 |
| 富文本编辑器、附件 / 图片上传 | 与 SSM 框架能力无关 |
| Elasticsearch、消息队列、Redis、微服务拆分 | 单机单体足够承载课程数据量 |
| LLM 作为**必选依赖** | 答辩现场无外网就演示不了。见 §7.5：LLM 只在有密钥且规则未命中时调用，没 key 时规则模式完整可用 |
| 智能体自动写站点地图 | 站点地图必须从代码反射得到，人工维护的那份只允许是"补充描述"（见 §7.3） |

## 3 系统架构

### 3.1 分层与分包（评分表 0.5 分「工程结构」）

按**业务分包**而非按层分包（这是"企业级"与"实验级"的区别，答辩要讲）：

```
com.ylf.cms
├─ CmsApplication.java
├─ common/
│   ├─ result/        Result<T>、PageResult<T>、ResultCode 枚举
│   ├─ exception/     BizException、全局异常处理器
│   ├─ annotation/    @RequirePermission、@Log
│   ├─ constant/      状态枚举、常量
│   └─ util/          排序字段白名单、脱敏工具
├─ config/            WebMvcConfig（拦截器注册）、MybatisPlusConfig（分页/乐观锁插件）、JacksonConfig
├─ auth/              LoginInterceptor、PermissionAspect、UserContext（ThreadLocal）
├─ module/
│   ├─ user/          controller / service / mapper / entity / dto / vo
│   ├─ role/
│   ├─ category/
│   ├─ article/
│   ├─ log/
│   └─ portal/        前台游客页（列表、详情）
├─ guide/             ★ 智能体：见 §7
│   ├─ sitemap/       SiteMapCollector、GuideCardResolver
│   ├─ intent/        IntentRouter（规则）、LlmIntentRouter（可选）
│   ├─ service/       GuideService、SuggestionService
│   ├─ controller/    GuideController
│   └─ model/         GuideCard、GuideRequest、GuideResponse
└─ resources/
    ├─ mapper/        XML（多表 join 用）
    ├─ templates/     Thymeleaf 页面 + fragments/guide.html
    ├─ static/        css / js
    ├─ guide/         site-map.yaml（只放文案：说明、步骤、提示、高亮选择器）
    └─ sql/           schema.sql、data.sql
```

`guide/` 独立成包，不塞进 `module/`——它是横切能力（要读所有 Controller），与业务模块是"消费者 / 被观测"关系，放一起会形成循环依赖。

**最终实现与学生原稿的差异**：检索别名（`aliases`）写在 `@GuideCard` 注解上，不单独建 `synonyms.yaml`——别名描述的是"这个页面还能叫什么"，属于页面结构的一部分，跟卡片放在一起才不会改漏；主动建议由 `SuggestionService` 用 Java 规则 + SQL 计数算出（见 §7.6），不建 `suggestions.yaml`，因为文案要带上实时数字（"你有 2 篇被驳回"），配置文件只能写死模板。

### 3.2 请求链路（答辩时画这张时序）

```
浏览器
  └─> LoginInterceptor        未登录 -> 401 / 跳登录
        └─> PermissionAspect   @RequirePermission -> 查权限集 -> 无权限 403
              └─> Controller(arg 校验 @Validated)
                    └─> Service（归属校验：作者只能改自己的）
                          └─> Mapper
  <── Result<T>  <── GlobalExceptionHandler（异常统一转换）
  ↑ LogAspect 在切面链里记录写操作 -> sys_log
```

**切面顺序必须显式指定**：`@Order(1)` 日志切面 → `@Order(2)` 权限切面，或者反过来但要保证**被 403 拦下的请求仍然留日志**（这本身就是评分表的"可追溯"）。

### 4.3 索引与检索优化（对应评分表「SQL 专项优化」1 分）

| 查询 | 索引 | 说明 |
|---|---|---|
| 文章列表（状态 + 分类 + 时间倒序） | `idx_article_query (status, category_id, create_time)` | 联合索引左前缀 |
| 标题模糊检索 | `idx_article_title (title)` | 实际 SQL 是 `LIKE '%kw%'`，**用不上这个索引**；保留它给前缀查询和等值查询，并在报告里用 `EXPLAIN` 对比 `%kw%` 与 `kw%`，说明"索引失效"的成因 |
| 按作者查自己的文章 | `idx_article_author (author_id, status)` | "我的文章"是高频路径 |
| 日志查询 | `idx_log_time (create_time)`、`idx_log_user (user_id)` | — |

> 报告里要写清：为什么没选全文索引（MariaDB ngram 对中文分词质量不可控，课程数据量下收益不抵复杂度）。这是取舍，不是遗漏。

### 4.4 MyBatis-Plus 高级特性清单（评分表 1 分，逐项打勾）

| 特性 | 落点 | 演示方式 |
|---|---|---|
| 分页插件 | `PaginationInnerInterceptor` | 文章列表翻页，`Page<T>` |
| 乐观锁 | `OptimisticLockerInnerInterceptor` + `@Version` | 两个浏览器同时编辑同一篇，后提交者拿到 409 |
| 逻辑删除 | `@TableLogic` + 全局配置 | 删除后查库仍在、查询不出现 |
| 自动填充 | `MetaObjectHandler` | `create_time` / `update_time` / `create_by` 不手写 |
| 字段策略 | `@TableField(select=false)` | 密码默认不查出 |
| 条件构造器 | `LambdaQueryWrapper` | 多条件检索 |
| 批量操作 | `saveBatch` / `updateBatchById` | 批量发布 100 条 |
| 防全表更新 | `BlockAttackInnerInterceptor` | 演示一次"无条件 update 被插件拦截" |

**已知坑（来自实验二经验，提前规避）：** 内部拦截器是有序链，**分页插件必须第一个加**——顺序错了会出现"分页失效"却没有任何报错。本项目顺序为：`PaginationInnerInterceptor` → `OptimisticLockerInnerInterceptor` → `BlockAttackInnerInterceptor`。乐观锁要生效，实体必须有 `@Version` 且 `updateById` 传的对象要带原 version 值；传新对象且 version 为 null 时，乐观锁不会报错、而是静默跳过。

## 5 基础核心功能任务分解（评分表 6 分）

每个工作包都按「输入 → 产出 → 完成判据」写，判据必须**能失败**（不能写成"功能正常"）。

### WP-1 用户权限管理（2 分）

| 项 | 内容 |
|---|---|
| 输入 | 六表 DDL、权限点清单（需求分析 §3.2） |
| 产出 | 注册 / 登录 / 退出；角色分配；`@RequirePermission` + `PermissionAspect`；数据级归属校验；管理员锁死保护（ADMIN 角色必须保留 `role:manage`，且最后一个可用管理员不能停用/删除） |
| 完成判据 | ① 未登录访问任意 `/api/**` 返回 401 且不落业务 SQL；② 作者账号调 `POST /api/articles/{id}/approve` 返回 **403**，且 `sys_log` 有一条 `result=DENIED`；③ 作者 A 调 `PUT /api/articles/{B的文章id}` 返回 403（**横向越权**）；④ 退出后原 Session 再访问返回 401；⑤ 尝试取消 ADMIN 的 `role:manage` 返回 409 且权限未变更 |
| 常见坑 | 权限从 Session 取，不要从请求参数取；`UserContext` 必须 `finally` 里 `remove()`，否则线程池串号 |

### WP-2 内容分类管理（1.5 分）

| 项 | 内容 |
|---|---|
| 输入 | `cms_category` |
| 产出 | 3 级树 CRUD、排序值调整（同级 `sort ASC, id ASC`）、启停、删除保护 |
| 完成判据 | ① 新增第 4 级返回 400 `CATEGORY_LEVEL_EXCEED`；② 删除含子分类或有文章引用的分类返回 409，且数据未被逻辑删除；③ 停用分类后，该分类下文章不可被新发布（已有文章不受影响）；④ 排序值改后列表顺序变化 |
| 常见坑 | 排序不能只靠 `sort` 值相等，要给唯一 tiebreaker（`sort ASC, id ASC`），否则翻页次序抖动 |

### WP-3 文章内容管理（1.5 分）

| 项 | 内容 |
|---|---|
| 输入 | `cms_article` + 状态机（需求分析 §5.1） |
| 产出 | 新增 / 编辑 / 批量发布 / 下架 / 删除 / 分页 / 多条件模糊检索 / 审核流转 |
| 完成判据 | ① 状态机 7 条边逐条走通（DRAFT→PENDING→PUBLISHED/REJECTED/DRAFT，PUBLISHED→OFFLINE，OFFLINE→PENDING，REJECTED→DRAFT）；② 非法迁移（如 PUBLISHED → 直接编辑）返回 **409 `INVALID_STATE`** 并给出当前状态；③ 驳回不填意见返回 400；④ 批量发布 100 条后，`sys_log` 有 100 条或 1 条带 count 的汇总（二者择一，但要在文档里写明口径） |
| 常见坑 | 状态机校验写在 Service 里用枚举 + `canTransferTo()`，不要散落 if；批量操作要控制事务粒度，别 100 条一个事务超时 |

### WP-4 系统基础运维（1 分）

| 项 | 内容 |
|---|---|
| 输入 | 全局异常、校验、日志切面 |
| 产出 | `Result<T>` 统一结构；`GlobalExceptionHandler`；`@Log` 切面；参数校验分组；敏感字段脱敏；排序字段白名单 |
| 完成判据 | ① 任意未捕获异常返回 `{code:500xxx, message:"...", data:null}`，**响应体不含堆栈、不含 SQL**；② 传 `pageSize=99999` 返回 400；③ 传 `sort=; DROP TABLE` 返回 400（白名单拒绝）；④ 日志中密码字段显示为 `***` |
| 常见坑 | 统一返回的 `code` 要分段（4xxxx 业务 / 5xxxx 系统），别全用 500；异常处理器要 `@Order`，否则可能被 Servlet 容器默认页抢走 |

## 7 ★ 站内引导智能体（本次新增重点）

### 7.1 用户看到什么（先用场景说清功能，再谈实现）

> **场景 1｜新人第一天**
> 作者小王登录，右下角有个小圆球，点开写着「不知道从哪开始？问我」。
> 他打字：「我想发一篇文章」。
> 智能体回：「发布文章需要经过审核。先起草 → 提交审核 → 审核员通过后才会上架。你可以从这里开始：」
> 下面铺两张卡：
> ```
> ┌─────────────────────────┐  ┌─────────────────────────┐
> │ 📝  写新文章              │  │ 📋  我的文章              │
> │ 起草、编辑草稿并提交审核     │  │ 查看草稿、被驳回的文章       │
> │ 需要权限：article:create  │  │ 需要权限：article:read     │
> │        [ 去这里 → ]       │  │        [ 去这里 → ]       │
> └─────────────────────────┘  └─────────────────────────┘
> ```
> 点第一张卡直接跳到写文章页，并高亮标题输入框。

> **场景 2｜权限不够**
> 小王问：「怎么管理用户？」
> 智能体回：「用户管理需要 `user:manage` 权限，你当前的作者角色没有这个权限。需要联系管理员分配。」
> 同时给一张**置灰卡**（不可点）+ 一张可点的「查看我的角色」卡。

> **场景 3｜主动建议**
> 小王打开对话框，还没问，智能体先说：「你有 2 篇文章被驳回，需要修改后重新提交。」
> 附一张「被驳回的文章」卡。这条建议**来自数据库计数**（`status=REJECTED AND author_id=我`），不是模型猜的。

> **场景 4｜问不存在的东西**
> 小王问：「怎么导出 Excel？」
> 智能体回：「系统目前没有导出功能。相关的可能是：」+ 「文章列表」卡。
> **不编造不存在的按钮。**

### 7.2 「智能体知道网站结构」——三条路线与选型

| 路线 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 反射后端代码** | 启动时遍历 `RequestMappingHandlerMapping` 拿到全部映射，配合自定义注解 `@GuideCard` 取页面元信息 | 与代码天然同步，不可能漂移；零人工维护；答辩能讲清原理 | 只能覆盖"接口"，页面上非接口的能力（如静态页、导入按钮）覆盖不到 | **采用** |
| B 反向解析前端 | 抓取 / 解析路由表或页面 DOM 生成地图 | 页面视角更直接 | 脆弱：前端一改就失效；受登录态影响；本质是"爬自己的站"，工程价值低 | 不采用（但作为"为什么不选"写进报告，体现取舍） |
| C A + 补充元数据 | A 提供结构真源，一份 `site-map.yaml` 只补充**描述性**字段（一句话说明、操作步骤、提示） | 结构不会漂移（真源仍是代码），描述可精修 | 需要启动期校验两边的 id 对得上 | **采用** |

**关键设计（这条是加分点，答辩一定要讲）：**

> 站点地图的**结构**（有哪些页面、路由是什么、需要什么权限）**只来自代码反射**；
> `site-map.yaml` 只允许补充**文案**，不允许新增页面。
> 启动时双向校验，对不上直接**启动失败**（fail-fast）。

这样一来，"智能体清楚网站结构"不是一句承诺，而是**启动期的硬约束**——代码里加了个 Controller 忘了标注解，服务起不来。没有任何"文档忘了更新"的可能。

### 7.3 数据模型

#### `@GuideCard` 注解

```java
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface GuideCard {
    String id();                        // 唯一，如 "article.create"
    String title();                     // "写新文章"
    String group();                     // "内容" / "账号与权限" / "系统" / "前台"
    String route();                     // 前端页面路径 "/articles/new"
    String summary();                   // 一句话，≤ 40 字
    int order() default 100;            // 卡片排序
    boolean page() default true;        // false = 纯数据接口，不出卡片
    String[] aliases() default {};      // 检索别名："发布,投稿,发表"
    String[] steps() default {};        // 操作步骤
}
```

#### 运行时卡片模型 `GuideCardVO`（返回给前端的字段）

| 字段 | 来源 | 说明 |
|---|---|---|
| `id` / `title` / `group` / `route` | 注解 | 卡片本体 |
| `summary` / `steps` / `tips` | yaml 覆盖注解（yaml 可缺省） | 文案 |
| `permission` | 方法上的 `@RequirePermission` | 决定卡片可见 / 置灰 |
| `httpMethod` / `apiPath` | 反射自 `RequestMappingInfo` | 卡片展开时给管理员看，用于"这卡背后是哪条接口" |
| `accessible` | 按当前用户权限集计算 | `false` → 前端置灰 |
| `matchScore` | 意图路由 | 仅调试用，生产可关 |
| `highlightTarget` | 从 `steps` 里的 `[data-guide-target=xxx]` 约定推导 | 跳过去后高亮哪个元素 |

#### `site-map.yaml`（只放文案）

```yaml
cards:
  article.create:
    summary: "起草新文章，写完后提交审核"
    steps:
      - "填写标题和摘要，摘要会用于列表展示"
      - "选择分类（最多三级）"
      - "写正文后点「提交审核」，状态变为待审核"
    tips:
      - "被驳回的文章修改后会回到草稿状态，需要重新提交"
    highlight: "#article-title"
```

### 7.4 采集与校验（`SiteMapCollector`）

**采集流程**

1. 注入 `RequestMappingHandlerMapping`，取 `getHandlerMethods()`；
2. 对每个 `HandlerMethod`：读类 / 方法上的 `@GuideCard`；读 `@RequirePermission` 的权限码；
3. 从 `RequestMappingInfo` 取 HTTP 方法与路径（Spring Boot 2.7 用 `getPatternsCondition().getPatterns()`；**注意**：Boot 3 / Spring 6 换成 `PathPatternParser`，`getPatternsCondition()` 会被弃用——本项目固定 2.7，但要在代码注释里写明，否则将来升级会莫名其妙拿到空集合）；
4. 合并 yaml 文案，生成 `SiteMap`（`Map<String, GuideCardVO>`）；
5. `GET /api/guide/pages` 暴露给前端 / 测试。

**启动期校验（不通过直接抛异常，让服务起不来）**

| # | 校验 | 不通过的后果 |
|---|---|---|
| C1 | `page=true` 的卡片 `id` 全局唯一 | 重复 id → 启动失败 |
| C2 | 所有带 `@RequirePermission` 的 Controller **整类**必须至少有一张 `@GuideCard` | 某个模块一张卡都没有 → 启动失败（保证"全站无遗漏"）。粒度是**类级**而不是方法级：同一个 Controller 里返回数据的辅助接口不需要各挂一张卡，但整个模块不能被漏掉 |
| C3 | 卡片声明的权限码必须存在于 `sys_permission` 表 | 写了不存在的权限 → 启动失败 |
| C4 | yaml 中的 key 必须是已存在的卡片 id（不允许凭空新增） | 拼错 id 而不报错 → 启动失败 |
| C5 | `page=true` 的卡片 `route` 非空且唯一 | 空路由 → 启动失败 |

> 实施建议：C1–C5 每一条写一个单元测试（不用启动整个容器，直接构造 collector 喂假数据），这样"校验真的有效"本身是可验证的。否则很容易写成"校验方法存在，但永远不会触发"。

**这里最容易踩的坑**：校验写成 `if (list.isEmpty()) throw` 但 `list` 永远是空——判据空转。所以每条校验必须配一个**会失败的测试**（给一个坏输入，断言抛异常）。

### 7.5 意图路由与对话

#### 两段式，L0 永远可用

```
用户输入
  ├─ L0 规则路由（默认，离线）──────────────► 命中卡片集 + 步骤号
  │   1. 归一化（去标点、繁简、全半角）
  │   2. bigram 倒排：title + summary + aliases + steps 建 2-gram 索引
  │   3. 打分 = 命中 bigram 数 / 查询 bigram 数 × 卡片权重
  │   4. 阈值 0.35 以下视为未命中 → 返回"没有这个功能" + 相关卡片 top3
  └─ L1 LLM 增强（需密钥：界面填写 / 服务端配置）──► 候选卡片 id 列表
      app.guide.llm.enabled=false
```

**为什么用 bigram 而不是分词**：引入 IK 分词要多一个依赖 + 词典，中文小词表场景 bigram 召回够用。这是一条可以在报告里讲的技术取舍。

**LLM 通道的硬约束（三条，缺一不可）**

1. **只做意图映射**：输入是"用户问题 + 候选卡片 id/标题/摘要"，输出是 JSON `{"answer":"...", "cardIds":["article.create"]}`；
2. **落地前校验**：`cardIds` 必须 ⊆ 站点地图 **且** ⊆ 当前用户可见集，否则整条丢弃、回落 L0；
3. **超时 2s + 异常静默降级**：任何失败都不影响 L0 结果，前端不提示报错，只在控制台 warn。

> 核心原则写进代码注释：**卡片的内容永远不经过模型**。模型只能"指向已有卡片"，不能"生成卡片"。这样即使 LLM 幻觉，也幻觉不出一个不存在的页面。

**多轮**：不做多轮。每次提问独立处理，不保留上下文；"先这样再那样"这类任务式对话明确写进"不包含"。理由：L0 是关键词匹配，硬拼上下文只会让匹配变模糊；真要支持指代，需要先有可靠的对话状态，那是本轮明确不做的范围。

#### 主动建议（`SuggestionService`）

纯 SQL 计数 + Java 规则，**不调模型**（没有 `suggestions.yaml`：文案里要带实时数字，配置文件只能写死模板）：

| 规则 | 查询 | 建议文案 |
|---|---|---|
| 有被驳回的文章 | `count(status='REJECTED' AND author_id=我)` | "你有 N 篇被驳回，修改后可重新提交" |
| 有待我审核 | `count(status='PENDING')` 且我有 `article:audit` | "有 N 篇待审核" |
| 从未发过文 | `count(article WHERE author_id=我)=0` | "还没发过文章，从写第一篇开始？" |
| 分类为空 | `count(cms_category)=0` 且我有 `category:write` | "还没有分类，先建分类再写文章" |

对话首次打开时返回建议；无建议则返回按 `order` 排的"常用入口"卡。

### 7.6 权限感知（安全边界）

| 规则 | 做法 |
|---|---|
| 卡片可见性 | `accessible = 当前权限集 ⊇ card.permission` |
| 无权限的卡片 | **置灰但仍展示**，写明缺哪个权限、找谁要（引导价值高于隐藏） |
| 卡片里不放数据 | 卡片只有"页面元信息"，不含任何业务数据；想看的必须点进去 |
| 跳转不是授权 | 点卡片只是普通页面跳转，**目标页仍走拦截器 + AOP**（双保险） |
| 智能体接口自身鉴权 | `/api/guide/**` 需要登录；未登录只返回"请先登录" |
| 日志 | 每次提问落 `sys_log`（`log_type='AI_QUERY'`，记录命中卡片 id，**不记完整输入原文**，避免用户误输入敏感信息） |

> 答辩可讲的点：智能体是一个"知道全站有哪些门"的角色，但它**没有钥匙**。它的回答里出现"用户管理"这四个字，不代表它能读用户表。

### 7.7 前端交互规格

**载体**：`templates/fragments/guide.html`，在所有页面 include；原生 JS 模块 `static/js/guide.js`。

| 元素 | 规格 |
|---|---|
| 悬浮球 | 右下 24px，56px 圆；未读建议时带红点；`aria-label="打开站内引导"` |
| 对话框 | 桌面 380×560 右侧抽屉；移动端全屏；Esc 关闭；焦点陷阱 |
| 消息流 | 用户右对齐气泡 / 智能体左对齐；智能体消息 = 一段文字 + 卡片网格 |
| 卡片网格 | 1–2 列自适应；卡片含 图标 / 标题 / 一句话 / 权限标签 / 主按钮 |
| 卡片展开 | 点击卡片 → 展开为步骤列表（手风琴），不再跳转；点「去这里 →」才跳转 |
| 置灰卡 | `opacity:.5`、`cursor:not-allowed`、鼠标悬停显示"需要 X 权限" |
| 跳转高亮 | 跳转带 `?guide=<cardId>`，目标页读参 → 给 `card.highlight` 元素加 `.guide-highlight` 类 2s（呼吸描边） |
| 状态 | 空态（"试试问我：怎么发布文章"）、加载中（三点动画）、无命中（"没找到，看看这些"）、未配置密钥时不提示（用户无感知） |
| 无障碍 | 所有可点元素 `tabindex` 可达；消息区 `aria-live="polite"` |

**不要做的事**：不要在卡片里塞截图。截图要维护 N 张图片，页面一改就过期，且和"结构从代码反射"的设计自相矛盾。用图标 + 文字就够了。

### 7.8 智能体验收判据（每条都能失败）

| # | 判据 | 失败长什么样 |
|---|---|---|
| G1 | `GET /api/guide/pages` 返回的卡片数 == 代码中 `page=true` 注解的个数 | 少一张 → 采集漏了 |
| G2 | 临时新增一个带 `@RequirePermission` 但**不挂 `@GuideCard`** 的 Controller，服务必须启动失败 | 能起来 → C2 校验空转 |
| G3 | 把 yaml 里某个 key 改成不存在的 id，服务必须启动失败 | 能起来 → C4 校验空转 |
| G4 | **断网**（`llm.enabled=false` 或拔网线）时，§7.1 四个场景全部正常 | 任一场景报错 → L0 不独立 |
| G5 | 作者账号请求"用户管理"卡：返回中存在该卡且 `accessible=false` | 返回里根本没有 → 违背"置灰可见"设计（需确认这是有意为之） |
| G6 | 提问"怎么导出 Excel"：返回的 `cardIds` 全是站点地图中真实存在的 id，且回答文本不含"导出"按钮描述 | 出现"点击导出" → 幻觉 |
| G7 | 用 L1 故意让它返回 `cardIds:["user.manage"]`（作者身份）：必须被过滤掉 | 透出 → 权限校验没落地 |
| G8 | 作者点开置灰卡（若能点到）直接访问 `/users` → 403，且页面不渲染任何用户数据 | 渲染了空表 → 越权面 |
| G9 | 每个卡片的 `route` 用 curl 请求（带对应角色 Cookie）返回 200 | 404 → 路由与代码漂移 |

> G2 / G3 / G7 是"注入式"判据——故意造一个坏输入验证防线有效。只测"正常情况返回对"是不够的（正常情况在没写校验时也会对）。

## 10 时间不够时的砍项顺序

## 12 决策记录

| 编号 | 决策 | 结论 | 理由 | 若选另一边的代价 |
|---|---|---|---|---|
| **Q-01** | 认证 Session 还是 JWT | **Session（已定）** | 同源 Thymeleaf，退出简单；AOP 与智能体取当前用户都更直接 | JWT 要写签发/解析/黑名单，多约 0.5 天且与"退出"语义打架 |
| **Q-02** | 前端做到什么程度 | **管理端 8 页 + 前台 2 页，原生 ES Module（已定，比原计划多用户/角色/日志 3 页）** | 智能体必须有 UI 载体；但不引前端工程，保证 `java -jar` 一键起 | 用独立 Vue 工程要多一套构建 + 跨域 + 部署，风险大于收益 |
| **Q-03** | 智能体知识源 | **A + 补充文案（路线 C）（已定）** | 结构从代码反射，不可能漂移；启动校验把"知道全站"变成硬约束 | 纯反向解析前端，页面一改就失效，且答辩讲不出技术含量 |
| **Q-04** | 智能体是否接大模型 | **接，用户自填密钥（已定）** | 不填 key 时离线可完整演示；填了能讲 AI；密钥只存会话 | 硬编码服务端 key → 既断网即废、又有泄密风险 |
| **Q-05** | 分类层级 / 审核记录建表 | **3 级 / 不单独建表（已定）** | 与 D1 暂定一致；保持"六表"口径 | 建审核表会引出"到底几张表"的口径问题 |

> 五项均按推荐执行，本文件即 v1.1 定稿，实现与之对齐。Q-02 的"8 页"来自评分表对"运维/权限/日志"的显式要求，不是范围蔓延。
